# 锴诚对接说明

## 总体调用关系

```text
青山成果抽取 ─────────────┐
                          ├─ 项目结构化证据 ─┐
单良Search ─ 外部发现 ────┘                  │
                                             ├─ run_attribution ─ 贡献结果 + 未解决事项
项目数据集 + 模型响应 ─ run_purification ────┘
```

数据提纯与AI贡献归因可以分别调用。归因不要求先运行数据提纯，提纯结果也不应被自动解释为AI贡献证据。

## 通用接口与回归夹具

`run_purification` 和 `run_attribution` 是通用入口。`examples/` 只用于回归验证当前版本仍能复现冻结案例，不应把示例项目名称、数值或结论复制到新项目输入。新项目必须由上游按Schema生成自己的结构化输入。

归因采用保守规则：明确为因果对照、双方单位与条件已锁定、结果方向为改善且单独因素及控制证据齐全时，才形成限定范围内的直接增量；部分可比只保留描述，不形成因果增量；可比性未知、结果无变化或变差、以及仅描述性比较都不能形成正向独立增量。证据不足的事项进入未解决事项，不由本工具自动裁决。

## 推荐接入方式

总体系统后端直接导入：

```python
from dca_integration import run_attribution, run_purification
```

前端只需展示：上传、执行状态、结果文件。算法明细和日志不必暴露在评审页面。

## Search结果映射

Search模块的每项外部发现映射到 `search_findings`：

| Search状态 | 归因输入status | 输出分类 |
|---|---|---|
| 外部证据与项目说法不一致 | `conflicts` | 查到但冲突 |
| 已检索但缺少关键材料 | `not_found` | 已检索仍查不到 |
| 材料存在但需要领域判断 | `needs_expert` | 需要专业判断 |

必须同时传递来源定位和相关项目声明。Search发现不能直接证明项目自身成果，也不能替代同条件实验对照。

## 模型调用

本包不持有模型客户端。若总体系统需要把原始材料自动整理为 `dca-attribution-input/v1`，建议由总体系统统一调用模型，再用Schema校验后传入本包。这样API Key、重试、限流和审计均由一个位置管理。

模型只能协助整理因素、声明、基线和外部发现。数值复算、ID一致性、状态边界和结果文件生成由本包确定性完成。

## 返回和异常

- 正常返回：Python字典形式的运行摘要；详细结果写入 `output_dir`。
- 输入缺字段、引用未知证据或因素、模型划分重叠等情况：抛出 `ValueError`。
- 重复ID、重复样本-模型响应、NaN/Infinity、比较单位不一致、候选不足或分组覆盖无法满足：抛出 `ValueError`，不静默覆盖或缩减要求。
- 文件不存在或不可读：抛出标准文件异常。

总体系统应在任务级目录中为每次运行创建独立 `output_dir`，不要让不同项目覆盖同一输出目录。

当前版本的工程行为已经过自动化回归和反例测试；项目级科学判断准确性仍需通过真实案例和专家结果校准。界面不得把本工具输出标记为真人专家结论或正式共识。
