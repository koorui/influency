# 成果名称输入：定位与自动建卡规则

本文件用于部署场景：用户可能只输入“拉曼探针”“NMRexp”“结构反演”等成果名称或简称，而不是完整成果表。

## 1. 目标

把用户的自然语言输入解析成一个边界清楚、可追溯的正式送检样本。不要把“名称检索”与“评价”混在一起。

流程：

`用户输入 → 项目上下文 → 项目内检索 → 候选成果 → 实体归并/拆分 → 规范成果名 → 自动成果卡 → 正式评价`

## 2. 项目上下文优先级

1. 当前系统项目ID/工作区；
2. 用户显式项目名/编号；
3. 上传材料中的项目标识；
4. 会话内唯一且明确的项目上下文。

找不到项目上下文时：

- 允许做公开信息初筛；
- 不得判断项目期新增；
- 不得判断项目方自述依据；
- 不得输出正式L级；
- 返回“需要选择项目或接入项目材料库”。

## 3. 候选成果生成

至少使用以下信号：

- 名称/简称/英文名的文字匹配；
- 与成果类型共现（分子、材料、数据库、模型、平台、软件、装置等）；
- 关键指标、论文、专利、数据集名；
- 所属课题、负责人、参与单位；
- 材料中的“代表性成果/主要成果/创新点/进展”等结构位置。

不得只靠关键词相似度决定边界。

## 4. 归并与拆分

### 可归并

- 同一成果在不同材料中使用简称/全称；
- 同一成果的版本更新且材料明确描述为同一产品/模型/数据库的迭代；
- 同一代表性成果包含若干明确的子结果，且项目方本身把它们作为一项成果整体陈述。

### 不自动归并

- 同一课题下的不同模型/材料/分子；
- 同一技术路线产生的多个独立成果；
- 仅因为关键词相似或负责人相同；
- 前期基础与项目期新增版本没有明确对应关系。

## 5. 置信度门控

### high

候选唯一，且至少两处项目材料能对齐名称/描述/指标中的两个以上要素。可以自动继续。

### medium

候选基本明确，但存在版本、子成果或命名边界问题。前台显示轻量确认。

### low

存在多个合理候选，或材料证据不足。必须先确认成果范围，不能自动进入正式评价。

## 6. 自动成果卡

成果卡是内部统一中间层，不要求用户手填。每个字段均保留：

```json
{
  "value": "...",
  "status": "confirmed|partial|missing",
  "sources": [
    {
      "file": "...",
      "page_or_location": "...",
      "quote": "...",
      "screenshot_ref": "..."
    }
  ]
}
```

系统摘要与项目方原文要分开。系统可以把多个原文整理成一句短摘要，但必须能回溯，不得改写成项目方从未声明的结论。

成果凝练按 [专家执行规则第一节](expert-method.md)：保留具体对象/版本、问题、原有基础、本期新增、基本验证、使用者/任务/结果及时间来源。支持性成果按其实际作用凝练，不只摘论文和产品名称。基本验证尚未完成或缺少相应证据时，平台建卡返回 `insufficient_validation_evidence`，在 `gaps` 区分“未提供依据”和“材料明确尚未完成”，保留卡片等待补充；不伪装成名称歧义，也不编造L1。

## 7. 前端交互

默认只展示：

- 规范成果名；
- 成果形态；
- 已关联材料数/原始依据数；
- `确认并评价` / `修改成果范围`（仅中低置信时出现）。

不要在首页铺出别名解析、候选打分、检索日志。
