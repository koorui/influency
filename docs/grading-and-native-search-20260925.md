# 当前判级标准与CLI自主检索

## 标准来源

用户提供 `科研成果六级影响力分级及理论依据-09251930.docx`。原文按段落和表格顺序保存到两个评价skill的 `references/grading-standard-20260925.md`，结构化L级和七维定义保存到同名JSON；标准版本为 `grading-20260925-1930`。Word没有完整的逐维G1–G5档位表，原有G档规则在不冲突处沿用；最终输出政策是用户本次另行明确的要求。

两套评价现在共享：L1成果形成与验证、L2局部作用验证、L3外部应用验证、L4专业方向显著影响、L5领域基础能力、L6重大引领影响。D6从仅限浦江接入恢复为流程、平台或组织能力集成。D7看独立第三方评测、专业采用和权威认可，不以自有论文、专利或关注数直接证明认可。

完成报告必须包含明确L级和七个G级，模型结构化输出及发布校验都检查。证据少时以现有事实给出保守等级和判断边界；无更高档依据的G1表示本轮材料范围的基档，不表示现实中绝无影响。项目日期、实际事件日期和报告形成日期仍分开，日期缺项不清空当前成果状态，也不能被用来倒推历史事实。

## 原Search问题

旧工单10次公共索引请求均HTTP 200，不能说网络请求全部失败。旧实现把策略限制在计划—固定抓取—总结三步，下游只看到8条项目摘录，没有充分利用原件中的日期和文献线索。最终只打开2个来源：一个403，另一个仅91字导航，无法形成有效外部依据。

另外，程序严格要求技术文献同时具备公开日和事件日，造成已有发表日期的技术背景也被排除。现在技术文献可用真实发表日期界定其公开时间；采用、使用等事件仍需自己的日期，不能拿发表日替代。

## 当前执行方式

用户随后明确要求由Docker中的CLI自主完成调查，多使用web search。因此正式主流程已切换为 `pipeline_native_search.collect_cli_research`；`collect_for_stage` 保留作历史兼容工具，不再作为当前工单入口。

CLI使用现有codex-relay、gpt-6-astra、high，配置 `web_search="live"`，可读完整材料并自主决定关键词、打开来源、追踪引文和改词再查。Search研究时间上限30分钟，普通阶段调用上限15分钟；没有必须找到正面结果的配额。原生实时搜索配置依据 [Codex官方配置文档](https://learn.chatgpt.com/docs/config-file/config-basic)。已在容器中实际观察到原生web_search查询、返回网址和打开结果事件，能力探测与工单证据分目录保存。

skill内 `research_session.py` 由CLI主动调用，直接从本次工具事件获取真实查询和网址，并按CLI选择归档来源。宿主程序只校验查询对应实际原生调用、网址确实出现在工具结果中、引文与原文及时间范围一致。CLI的人工诊断以外结果不混入工单。

原始材料、工具事件、访问失败和旧报告均保留。Search解析和归档脚本中的旧摘要计算功能已移除；没有用另一种摘要替换。Docker底层镜像协议未改动。
