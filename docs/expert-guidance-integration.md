| 专家意见 | 实际落实 |
| --- | --- |
| 评价具体成果已有作用 | 凝练对象/版本、问题、原有基础、本期新增、验证、使用者/任务/结果及时间来源 |
| 先辨明成果是否成立 | 增加“基本验证依据不足”的建卡状态，保留卡片等待补证，不靠L1填满输出 |
| 不统一所有成果的证明材料 | 分别描述科学发现、方法、模型/软件/数据、装置和平台的作用路径；学术影响不以商业化为前提 |
| 合作使用不等于独立采用 | 核查真实需求、自主选择与利益关系；单位名称不同或相互出证明不足以认定独立 |
| 高等级取决于作用的变化 | L4查持续作用，L5查相关领域稳定依赖，L6查实质改变；不统一设人数门槛，不强制逐级经历 |
| 共同成果与各方贡献分开 | 区分整体作用、参与者工作、本期新增与AI净增量，避免重复计功 |
| 支撑性工作应获得识别 | 从公共能力被任务使用、产生结果、后续复用三个环节核查，不把接入图当闭环 |
| 评价服务管理而非制造排名 | 提出试用、观察、维护和补证行动；影响级别不换算成人才、经费或调度级别 |

## AI与专家的职责边界

附件提出“不由AI自动定级”，当前平台产品约定则是自动生成明确等级并交付。此次按“系统提供有依据的等级建议，专家确认关键事实和最终认定”的边界更新skill：`formal`仅表示系统输出完成，不是专家认证；报告摘要应说明建议性质，缺记录和专业争议分别安排补证与核验任务。

此调整没有实现新的专家签字、回避、申诉或审批功能，也没有把用户验收当作专家复核。要使产品严格实行“专家确认后才形成正式等级”，还需单独设计专家角色、复核记录和报告状态。这是制度与产品流程调整，不能靠改一段提示词宣称完成。

## 运行接入与历史结果

建卡和管理者评价的实际提示词均载入专家规则；七维引擎的维度判断、成果综合及范围综合也读取同一文件。检索规则补充独立性、时段、去重与非公开证据边界；归因准备补充各方贡献及回流事实。

两个旧技能名改成统一技能的兼容入口，避免指向已经不存在的独立脚本或采用另一套规则。新运行记录新版本，交接读取实际运行版本，缺失或旧版本保持历史/混合标记。历史报告不会自动重评。

## 审阅时可用的边界例子

以下是判断规则的示例，不是已运行的项目评价结果：

- 只有方案、演示计划或“验证工作正在开展”：先保存凝练结果，缺少基本验证时不编造L1。
- 数据集通过质量检验，尚无真实使用：在成果边界与有效性依据充分时可支持L1，不因未商业化而否定成果。
- 科学发现被独立团队实质用于后续发现：检查真实学术作用，不能只因没有产品用户而封顶L1。
- 合作单位出具采用证明：先辨明任务、结果与关系，自主选择和独立性未经核实不能直接支持L3。
- 小领域工具长期嵌入专业流程：按该领域稳定依赖判断L5条件，不强求跨领域人数；一次试用仍不足。
- 用户很多或发布了标准：继续核查依赖及改变，不能凭流量或标准名称直接判L5/L6。

首轮离线检查只验证规则是否传入、补证状态及版本追溯，当时没有真实模型试评；后续实跑结果见下节。

首轮实施检查结果：`test_expert_guidance.py`、`test_intake_transport.py`、`test_current_grading_standard.py` 共13项通过；涉及的6个技能通过格式校验，改动通过差异格式检查。这些离线检查使用隔离SQLite和替代模型传输，没有读写正式数据库或发出模型请求。
