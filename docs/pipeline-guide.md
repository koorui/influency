## 新成果从哪里进入

1. 项目方在 `/submit` 登录后填写代表性成果表，每份表只描述一个具体成果，上传文件、文件夹或ZIP。没有依据的可选数据不要估算。
2. 提交生成工单；项目方在“我的需求”查看状态。已有成果查询只联想已发布成果，不会每次查询重新调用模型。
3. 管理员在“材料库”检查用途。项目材料可评测；参考评价和流程说明只保管，不作本次项目原始依据。也可在材料库批量上传。
4. 在“完整工作流”展开新建表单，选择工单，带入项目、填报材料和日期；也可直接选择库中材料。

“吴老师单项评价”是保留的单模块入口。需要归因与双层结果时使用“完整工作流”。

## 工作流参数

- 项目ID须与v19交付一致。拉曼案例为P02。
- 本轮成果ID保持稳定。本例使用RAMAN-CASE-001，显式关联v19冻结子成果ACH-002，不把MAIN-003的其他成果归入探针。
- 实际Search填写项目执行起点、评审/统计截止日和依据。本例为2025-06-01的执行月份边界、2026-04-30截止，解释见 [时间复核](raman-review-date-audit.md)。
- 历史回放模式需同项目、同成果的search-replay.v1交付，不能标为本轮检索。
- v19使用indicator-workspace.v6交付。已有P02工作区位于原交付包 `系统运行版/backend/workspace_snapshots/P02.json`。浏览器读取文件内容，不接受任意服务器路径。

复现实测可先选project-original-pages.txt：从完整679页报告提取的33页相关原文，附原件SHA256和物理页码，不含参考评价。完整PDF已在材料库保存。

## 执行、等待和补充

`成果定位/建卡 → 实际Search或历史回放 → 原版DCA → 吴老师评价 → 原版v19 → 独立导出`

后台执行，不占用一次网页请求等待。歧义、缺日期或缺映射显示待补充；模型格式错误显示执行失败，不当作科研证据不足。

在弹窗补录检索方式、日期、材料或范围。评价冻结子成果时选择目标，再按当前底稿逐维度选择证据，填写范围说明并确认。材料、范围或Search变化后旧路由确认失效。不要照搬另一轮E1/E2等编号。

材料/范围变化从定位重跑；Search变化从检索重跑；仅v19映射变化从v19重跑。原尝试和修订保留。代码或Skill版本变化后需新建任务，不改写旧指纹绕过约束。

## 审核发布

吴老师报告可“转入报告审核”。同源重复导入幂等；来源更新则形成新草稿版本并保留历史。旧稿不能套用变化后的来源直接发布，已发布版本不被静默覆盖。

普通用户只看已发布报告。模型建议、结构校验和管理员审核是不同环节；v19的待确认是有效结果，不改成默认G1。

## 底稿与运行

任务位于 `backend/storage/pipelines/<id>/`，保存六阶段目录、引用、规则副本及调用记录。Search保留真实请求和原文，专门表格注明缺项；导出分别保存wu-evaluation.json和v19-evaluation.json。

`scripts/dev.ps1` 启动MySQL、API、单项worker、完整工作流worker和前端。完整工作流使用 `python -m app.pipeline_worker`，单项使用 `python -m app.worker`。先核对进程，不因日志暂时不更新就重启模型任务。

原件目录和MySQL须一起备份。限制与实测范围见 [验收记录](live-pipeline-acceptance-20260925.md)。
