# 吴老师工作流与 v19 评测模块：Skill 封装可行性评估

日期：2026-09-23。范围：阅读两份附件、静态检查交付包，并对三份项目快照执行输入契约的离线校验。未发起模型请求，未修改交付包、现有等级规则或平台运行适配器，未进行飞书写入和消息发送。

## 结论

可以封装。建议以吴老师的“成果级送检—核验—评价—行动”作为上层工作流，以 v19 的七维、证据路由、归因约束和结果检查作为可复用模块。

目前不能把两个来源原样拼在一起直接上线：六级含义不同，评价对象粒度不同，输入与输出格式也不兼容。Skill 的结构可成立，但正式评价口径必须显式选定。

## 实际检查的来源

- `outcome-impact-evaluation-SKILL.md`：已具备 name/description、执行步骤与交付格式，可作为入口草稿。

- 同目录 `evaluation_policy.py`、`d_dimension_framework.py`、`evidence_adapter.py`、`material_routing.py`、`external_claim_routing.py`：分级、七维21分支、组件契约和显式材料路由。

- `impact-platform/backend/app/schema.py`：当前平台报告契约。

## 两份 Markdown 的可复用价值

工作流明确区分项目方声明与独立核验，要求证据回溯、AI净增量归因，并将复杂的七维判断与简洁的管理者报告分开。这些应成为正式 Skill 的业务规则。

Skill 草稿缺失两份引用资源：`references/evaluation-rules.md` 与 `references/ui-spec.md`。在附件同级 references 路径及 v19 系统运行版中未发现同名文件。前者可从 v19 抽取七维规则，但必须处理下述分级差异；后者可依据完整工作流与 v14 HTML 整理。不能将缺失引用视作已经存在的规则。

缺材料应保留“待确认”；缺外部检索能力则标记未核验。固定 JSON 不要求把未知字段编造成事实。

## 关键差异：L 级不能直接互换

| 等级 | 吴老师流程 / 现有平台 | v19 实际代码 `L_LEVEL_CRITERIA` |
| --- | --- | --- |
| L1 | 成果形成与验证 | 在本项目真实任务中发挥作用 |
| L2 | 局部作用验证 | 独立外部主体实际使用或验证，且有可核验结果 |
| L3 | 外部应用验证 | 多支独立团队在同一专业方向持续采用并形成后续成果 |
| L4 | 专业方向显著影响 | 成为领域稳定依赖的平台、工具或能力 |
| L5 | 领域基础能力 | 广泛使用并改变领域开展工作的方式 |
| L6 | 重大引领影响 | 越出单一领域，形成广泛而持久的改变 |

这不是换中文名称能解决的问题，也不能统一加一。建议分别定义 `wu-outcome-v1` 与 `indicator-v19` 规则档案，在输入、输出及数据库中保存 `rubric_id` 和版本。平台当前展示口径与吴老师一致，建议默认采用此档案；若引入 v19 结果，必须按原始证据重新判断展示等级，或者连同原口径独立展示。

v19 的规则还将 D6 限定为浦江国家实验室 AI4S 主线集成。若日后评估其他项目，需要显式配置适用范围，不能把普通内部协作自动当作 D6。

## 输入门槛与样例检查

采用源码中已经阅读过的 `build_indicator_input_contract` 与 `_receipt` 两个纯数据函数，输入现有 JSON 快照执行校验；没有导入模型客户端或运行评价流水线。

| 项目 | 当前主要成果数 | 程序输入门槛 | 说明 |
| --- | ---: | --- | --- |
| P01 | 0 | 未通过 | 缺 Step 3 冻结成果；外部声明路由待核验 |
| P02：人工智能赋能有机化学 | 5 | 通过 | 冻结成果和专业事实均已接收；内部 Search 仍为上游未交付 |
| P06 | 0 | 未通过 | 缺 Step 3 冻结成果；外部声明路由待核验 |

输入条件“通过”只代表程序允许执行，不代表事实均已核验。源码将内部检索、AI贡献和外部检索列为非全局强制项，各维度仍需依据缺口给出待核验判断。

P02 当前五项主要成果以课题1至课题5为边界，下含分支成果。吴老师要求一个具体模型、数据库、材料等为送检样本；不能直接假定一项课题就是一项具体成果。封装需要支持上游成果整理与确认，然后冻结 ID；进入 v19 评价阶段之后，不再擅自合并、拆分或改名。

## 历史运行记录不能当作新等级结果

包内 P02 运行记录声明版本 v19、预期41个逻辑调用、完成41个逻辑调用，`formal=true`。trace 记录45次请求，其中41次成功、4次失败，说明存在失败后重试。

但五项成果的35个维度中均未找到 `grade.level`，五个 `synthesis.impact_level` 均缺失，项目综合也没有 `scope_impact_level`。不能仅凭版本字符串、`formal` 或成功调用数推断已执行现行分级；没有等级应显示未评定，不能自行补成 L1。

另外，工作区中仍有原开发者电脑的绝对材料路径；移植时需把来源改为材料 ID 和包内相对路径，并逐一检查原始文件、页码和引用是否可访问。快照有摘录不等于所有原件已完整随包交付。

## 可复用的模块与须补的接口

可复用：

- D1–D7 的21个原子分支和 G1–G5 条件。
- 内部、AI归因、外部证据的独立输入契约。
- 证据显式绑定、未匹配材料保留、时间窗限制、反证与缺口处理。
- 逐维度判断、成果综合、可选项目范围归纳的阶段划分。
- 来源 ID / 成果范围检查、结构化结果和运行记录。

需要补齐：

- 通用输入：材料清单、成果卡、冻结状态、评价时间窗、规则档案，替代仅以 P01/P02/P06 为入口的快照使用方式。
- 新项目的路由配置，避免沿用已有项目专用的映射和人工审阅表。
- 完整 JSON Schema：目前平台的简版 `Evaluation` 不能无损承载两种结果。
- 分离后台底稿和前台报告：保留七维原始判断、证据台账及归因记录；前台摘要保留理由到证据的引用、升级1级/2级、任务对象和文案。
- 当前平台证据对象需增加真实 URL、来源类型、物理页码、支持范围和不能证明的范围等字段；`reasons` 的纯字符串列表需支持证据引用。
- 将最小出处真实性、完整性和规则版本检查纳入发布前校验。结构正确不等于判断正确。

## 建议的封装形态

以下是拟定结构，不是已经安装或接入的 Skill：

```text
outcome-impact-evaluation/
  SKILL.md
  references/
    intake-and-evidence.md       成果整理、冻结与证据约束
    d1-d7-rules.md               七维规则和适用范围
    level-profiles.md            明确隔离的六级口径
    output-schema.json          完整机器可校验契约
    ui-spec.md                  管理者报告要求
  scripts/
    preflight.py                输入、版本、引用与材料可达性检查
    validate_result.py          输出与证据引用校验
    export_platform_report.py   保留底稿，输出平台报告
```

Skill 只打包可复用规则和必要脚本；项目材料、凭据、数据库连接、样例结论和前端整个应用不混入通用规则。

## 两种 Codex 执行路线

**推荐：Codex 按 Skill 执行规则。** 从 v19 提取规则和可复用校验函数；Codex 消费指定材料，逐阶段完成证据整理和评价，输出完整 JSON，由平台接收为草稿。此时不要求沿用 v19 的外部模型服务。

**备选：Codex 调用 v19 的现有流水线。** Skill 指导运行一个命令行包装器，包装器调用 `IndicatorEvaluationPipeline`。现有代码中的模型客户端使用 OpenAI-compatible Chat Completions 格式连接配置的服务，默认值涉及 DeepSeek/Kimi；它不是现成的 Codex 执行接口。仅由 Codex 启动脚本不会自动把底层评价模型替换成 Codex。

按现有流水线，每成果7次维度判断加1次成果综合，全项目再1次综合；P02 为 `5×8+1=41` 个逻辑调用，重试可增加请求数。采用此路线须配置对应服务凭据，并给后台任务设置进度、阶段结果、超时和重试边界。

本次尝试获取 OpenAI 官方 Skills / 非交互文档页面及 Markdown 版本均收到 HTTP 403，因此不把未经在线核实的 CLI 参数写作已验证接入方式。正式对接时还需针对本机 Codex 版本确认执行器与认证方式。

## 对当前系统的落点

管理员上传材料 → 整理成果与证据 → 输入检查和规则版本选择 → 后台 Codex 执行器加载 Skill → 输出完整底稿和展示 JSON → 程序校验 → 草稿预览 → 管理员发布 → 用户查询。

用户固定表单继续用于选择已有项目和记录需求；真正触发材料评判的是管理员后台任务，不因用户选择“评价任务”就把已发布报告冒充新评判。

下一步建议先用 P02 的一项具体成果做接入试验：确认成果边界和六级口径，补齐证据路径，完成最小 Skill 与输出校验，再替换 `MockAdapter`。P01/P06 先补冻结成果，不能关闭其输入检查来强行得到结论。
